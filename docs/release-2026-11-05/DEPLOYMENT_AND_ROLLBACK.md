## Deployment sequence (requires a later explicit deployment instruction)

1. Record tested API/mobile/admin revisions and artifact hashes, preserve all previous evidence, and resolve remaining dependency/provider/device gates. Inventory active client versions and existing jobs/payment states; current reports provide no fleet-version evidence.
2. Rehearse backups and restore with production-like data volumes, uploads, PostgreSQL, Redis jobs, and provider references. Establish measured RPO/RTO and an owner for failed payment/reconciliation alerts. This remains a release gate.
3. Prepare an enforced upgrade/maintenance window **or implement and test a compatibility bridge in a separate change**. The current hard requirements cannot safely be introduced by blindly deploying the API first or by publishing clients first. Stage compatible apps and verify consent, session continuation/reverification, protected files, chat retries and GPS before reopening business traffic. No such bridge or force-upgrade service has been implemented in this continuation.

## Payment recovery compatibility in this continuation

The Connect SCA recovery patch changes only internal API/worker calls: it uses the existing owned saved-card reference and pinned connected account to create a fresh clone, while retaining the existing PaymentIntent, booking attempt and stable confirmation keys. It adds no migration, response field or queue payload. A worker must also resume a canonical `requires_payment_method` + `authentication_required` result after a lost confirmation response; an older worker may cancel that recoverable state. Deploy API and embedded workers together after quiescing old consumers. Keep the original card/provider references and attempt keys across rollback. Do not roll back to the consumed-clone implementation for pending SCA cases; hold those actions and roll forward if a compatible recovery binary is unavailable.

Customer staging callbacks now use the staging scheme derived from the installed application ID in both StripeProvider and connected-account initialization. This requires a rebuilt APK. It does not change production or development callback schemes. Reverting to an older local APK loses this staging acceptance condition.

## Safe rollback

Rollback is a switch to a previously tested **contract-compatible** binary with the additive schema and retained evidence left in place. Do not roll back to the pre-remediation baseline merely because it boots: it reintroduces public-file, authorization, retention, retry and ordering defects and cannot honor current session/consent contracts.

Quiesce booking/payment ingress and stop all incompatible worker consumers before a binary switch. Preserve queue IDs, payment idempotency keys and provider result references. Reconcile pending/unknown authorizations/captures with the provider before retrying. Check that the target understands the existing financial/job states; payload similarity alone is insufficient. Resume compatible workers, prove a test job is consumed, then resume traffic.

Do not drop migrations, delete legal/financial history, restore an old DB snapshot over newer provider successes, remove family roots, reset app outboxes, or convert measuredAt back to receipt time. If no compatible binary is available, hold maintenance and roll forward. An independent restore rehearsal and an operator-run coordinated rollback have not been accepted; keep OPS-01 open.
